# План E (запасной): переделка механики пивота на системный скроллвью

Запускать ТОЛЬКО если T1/T2/T3 и диагностика не закрыли двоение.

## Принцип

Один горизонтальный **UIScrollView с pagingEnabled** — contentOffset единственный
источник правды, позиции страниц никогда не трогаем руками (никаких layer.position
в покадровом пути, никакого ручного кольца). Композитор сам рисует то, что видел
всю жизнь в системных пейджерах — артефактов «двух копий» там не бывает по
определению.

## Архитектура

1. **Скроллвью**: frame = зона контента (0, topInset+126, 320, остальное),
   `pagingEnabled=YES`, `contentSize = (4×320, h)`, `clipsToBounds=YES`,
   делегат — пивот. Страницы добавляются в него с x = i·320. Их `frame`
   выставляется ОДИН раз (обычные вьюхи в скроллвью — системный путь).
2. **Бесконечность** — имитация после остановки:
   - в `scrollViewDidEndDecelerating:`: если дошли до края, переставить
     `contentOffset` на эквивалентную позицию в середине диапазона БЕЗ
     анимации (`setContentOffset:animated:NO` — скролл уже стоит, скачка не видно);
   - для этого контент удвоить: 8 страниц (0..3 + 0..3), старт в первой
     половине; после остановки в половине k сдвигать offset на ±4·320, чтобы
     всегда оставаться во «внутренней» зоне. Перезаполнение данных не нужно —
     это те же 4 объекта страниц? НЕТ: скроллвью нужен уникальный контент на
     каждый слот → страницы-двойники = лёгкие контейнеры с перенаправлением
     на общие данные (города/будильники и так перечитываются из префов).
     Сначала сделать БЕЗ бесконечности (4 страницы, края-резинка системные) —
     приоритет: отсутствие артефактов > бесконечность (решение юзера).
3. **Заголовки и пары**: `scrollViewDidScroll:` → offset скроллвью; заголовки
   и пары двигать `transform` (не frame!) их ленты; параллакс заголовков —
   как сейчас. Пары 0–1 — по своим слотам.
4. **Параллакс контента**: ТОЛЬКО transform на внутреннем контейнере каждой
   страницы (не на самой странице — её двигает скроллвью): `t = 0.4 × (pageX −
   contentOffset)`, выставляется в `scrollViewDidScroll:`. Без растеризации.
   Скроллвью внутри страницы не трогаем.
5. **Квадрат таймера**: остаётся на корне пивота, позиция = 3·320 − offset + 75,
   обновляется в `scrollViewDidScroll:` + колбэк состояния (как сейчас).
6. **Жест осей**: пан пивота удалить — горизонталь забирает скроллвью,
   вертикаль остаётся страницам. Конфликт осей решается системно
   (скроллвью дождётся вертикального пана страницы).

## Что сохраняется как есть

Дизайн-канон (шапка 96/52, строки 56, пары light 24, тумблер 46×22), данные
(MPClockData), редактор, таймер/секундомер/квадрат, роллы цифр, kill-switch.
Отладочные команды (cslow/cadd/cdel/cscroll/cfinger/cdraglog/dump) — по месту:
cslow/cfinger переписать под новый драйв (анимированный setContentOffset).

## Порядок работ

1. Новый класс-драйв в MPClockPivotView (скроллвью + делегат) поверх тех же
   страниц; старый пан/applyBody удалить.
2. Сборка без бесконечности → палец-тест юзера (главный критерий).
3. Если чисто → бесконечность дублированием + перепрыжком после остановки →
   второй палец-тест.
4. Чистка: удалить诊断-инструменты из боевого пути (cdraglog оставить как
   отладку), снять маркер сборки.
